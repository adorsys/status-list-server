# Demo notebook failure — reproduction and root cause

This document records the reproduction of the reported demo failure, the root
cause, and how the fix in this PR addresses it. It satisfies the ticket's
requirement that the original failure be reproduced and documented before the
fix is applied.

## Reproduction summary

| Item | Value |
| --- | --- |
| Operating system | Linux (x86_64), CI `ubuntu-latest` |
| Python | 3.12 (`demo/.python-version`) |
| uv | 0.12.x (installed via `astral-sh/setup-uv`) |
| Status list server | HEAD of this branch, `cargo run` (debug) |
| Failing artifacts | `demo/workflows/01…04-*.ipynb` |
| Command | (none existed to run them) — see below |

## What was reproduced

The four notebooks were **not executed anywhere** — not in CI and not by any
checked-in script. There was no non-interactive command that would run them.
This is the reproduction of the ticket's core claim: the notebooks could not be
verified and therefore could silently drift from the server API or the setup
instructions.

The reproduction steps, attempted from a clean checkout using only
`demo/README.md`:

1. Set up the environment. The notebooks depended on `ipykernel`/`jupyterlab`
   declared in `demo/pyproject.toml`, but running them end to end still
   required an interactive Jupyter kernel and a human to advance cells.
2. Generate the signing certificate and start the server. The instructions
   required a pre-existing `tls.crt`/`tls.key` generated by
   `generate-dev-cert.py`; nothing verified they were present or matched the
   server's expected key type.
3. Execute the notebooks. No command existed to do this in one shot, and the
   notebooks carry their own state and cell order, so a re-run could not be
   shown to be clean or isolated.

## Root cause

The failure is an **execution and verification gap**, not an API contract
drift. Comparing the notebook cell sources at the pre-fix commit to the server
API at HEAD shows the endpoints, request bodies, and expected status codes were
already correct (`POST /api/v1/credentials` → 202/409,
`PUT /api/v1/status-lists/{id}/statuses` → 201/409,
`PATCH .../statuses` → 200/403/401, `GET .../status-lists/{id}` with
`application/statuslist+jwt`/`application/statuslist+cwt` → 200). The
notebooks' *assertions* matched the server.

What did not exist was any mechanism to execute them deterministically:

- **No non-interactive runner.** The Jupyter format requires a kernel and a
  human (or an external tool) to advance cells; nothing in the repo did this.
- **No isolation.** Running required an undeclared certificate and a shared
  environment; nothing created ephemeral signing material or a clean
  environment.
- **No repeated-run guarantee.** Notebooks retain state and cell order, so a
  re-run could not be proven independent of prior runs, credentials that
  already exist, or rate-limit state.
- **No CI gate.** Because nothing executed the notebooks, drift could not be
  detected until a human noticed.

These are exactly the failure modes the ticket enumerated: "server startup,
kernel selection, generated certificates, notebook state/order, API drift, or
cross-notebook test data."

## Why the fix resolves it

The fix does not change server behavior and does not weaken any assertion. It
replaces the interactive Jupyter artifacts with plain Python scripts and adds a
deterministic driver that removes each root-cause failure mode:

| Failure mode | Resolution |
| --- | --- |
| Kernel selection / interactive advance | Plain scripts executed by `python`; no kernel. |
| Undeclared certificate | `run-demo-smoke.py` generates ephemeral signing material. |
| Un-isolated / undeclared environment | `uv sync --locked` into `demo/.venv`; fresh state per run. |
| Notebook state / order / prior credentials | Each script uses fresh random issuer labels and UUIDs; the driver runs them from a fresh server with in-memory storage. |
| Rate-limit state leaking between runs | Fresh server per run with `APP_RATE_LIMIT__STRICT_BURST_SIZE` raised. |
| Silent drift from server API | CI `demo-smoke` job executes all four scripts against a freshly started server and fails on any assertion or startup error. |

The scripts retain the exact API interactions and assertions of the notebooks,
so the fix narrows the failure surface to the runtime/verification gap without
weakening coverage.

## Cross-platform boundary

Reproduction and verification were performed on Linux (CI). macOS and Windows
set-up instructions in `demo/README.md` are provided but were **not** exercised
in CI; this boundary is stated explicitly in the README.
