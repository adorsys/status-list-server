_A production use case for robust and long-lived secure applications_

[.lead]
The Status List Server needs AWS credentials for three things: Route 53 (ACME DNS-01 challenges), S3 (certificate storage), and Secrets Manager (credential sync via ESO). Historically, these lived in GitHub Secrets as permanent access keys. Now they don't have to.

== What's at Stake for a Server Like Ours

The Status List Server is an ACME-powered certificate issuer. That means it _must_ have AWS credentials at runtime — not just during CI. The credentials need to:

1. **Update Route 53** DNS records for ACME DNS-01 challenges during certificate provisioning and renewal
2. **Read/write S3** buckets for certificate storage
3. **Read Secrets Manager** through ESO for PostgreSQL and Redis passwords

A leaked access key doesn't just expose build pipelines — it exposes the live certificate infrastructure.

== The Problem with Static Access Keys

Static access keys (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`) are permanent. They exist in GitHub Secrets until someone remembers to rotate them, work from any branch or context, and live indefinitely once issued.

[%caption-off]
|===
| Static Keys | Workload Identity

| Permanent until rotated manually
| ~1 hour, auto-issued per pod

| Works from any branch or context
| Only from the assigned pod

| Two secrets to manage, audit, and rotate
| No secrets — GitHub provides the OIDC token
|===

== How It Works on the Status List Server

=== GitHub Actions (CI/CD)

The deploy workflow uses OIDC to get short-lived AWS credentials:

```
Push to main
  │
  ├─ CI passes, image pushed to GHCR
  │
  └─ Deploy workflow
        ├─ GitHub issues OIDC token (id-token: write permission already declared)
        ├─ Token exchanged via sts:AssumeRoleWithWebIdentity
        │    └─ AWS validates: repo + main branch + production environment
        ├─ helm dependency build && helm upgrade --install
        └─ App deployed to EKS
```

The IAM trust policy enforces three gates:

```json
{
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub":
        "repo:adorsys/status-list-server:ref:refs/heads/main:environment:production"
    }
  }
}
```

A feature-branch run or a PR cannot assume the production role — AWS rejects it at the token exchange stage, before any action runs.

=== Inside the Cluster (IRSA)

The running pod also needs AWS credentials for Route 53 DNS updates (ACME renewal runs inside the server) and S3 certificate storage. Instead of mounting a credential file:

```yaml
serviceAccount:
  create: true
  name: statuslist-sa
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/statuslist-irsa
```

The AWS SDK automatically discovers and uses the IRSA credentials. The server binary needs no changes — the Rust `aws-config` crate picks up the projected token from the ServiceAccount.

== What Changes in Practice

| Before | After |
|--------|-------|
| Rotate access keys every 90 days | No rotation — tokens refresh automatically |
| Pinned to one AWS account | IRSA role can be scoped per environment |
| Any branch can assume prod role | Trust policy enforces `main` + `production` env |
| Leaked key = permanent access | Tokens expire in ~1 hour |

The server's ACME renewal jobs (ran nightly via cron) now use short-lived credentials scoped to exactly what they need — nothing more.

== Setup

The minimal IAM inline policy for the IRSA role:

```json
{
  "Statement": [
    { "Effect": "Allow", "Action": ["route53:ChangeResourceRecordSets", "route53:ListResourceRecordSets"], "Resource": "arn:aws:route53:::hostedzone/*" },
    { "Effect": "Allow", "Action": "route53:GetChange", "Resource": "arn:aws:route53:::change/*" },
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"], "Resource": "arn:aws:s3:::status-list-adorsys/*" }
  ]
}
```

No `secretsmanager:GetSecretValue` needed at the pod level when ESO handles secret sync separately.
