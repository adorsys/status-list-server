# OAuth Token Status List - draft-21 Compliance Matrix

Audit of the status-list issuer/hosting implementation against
[draft-ietf-oauth-status-list-21](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/)
(Token Status List, expires 23 December 2026). All findings below were checked directly
against the primary IETF text. Complements the application-specific status value work tracked in #152.

Status legend:

- **Compliant** - behavior matches the spec, verified against implementation behavior.
- **Fixed** - deviated from the spec; corrected in this change.
- **Deviation (documented)** - intentional gap; the spec marks the feature OPTIONAL and no
  ticket deliverable requires it.
- **Out of scope** - belongs to another tracked ticket or component.
- **Hardening note** - not a draft-21 violation (SHOULD-level or unspecified), but worth
  tracking as a follow-up.

| 1  | §4.1        | Byte array compressed with DEFLATE ([RFC 1951]) in the ZLIB ([RFC 1950]) container                                                         | Compliant              | Status lists are encoded with zlib-wrapped DEFLATE, including the required zlib header and checksum trailer.                                                                                         |
| 2  | §4.1        | Highest compression level RECOMMENDED                                                                                                      | Compliant              | Status-list compression uses the highest available compression level.                                                                                                                                |
| 3  | §4.1        | Bits packed LSB (bit "0") → MSB (bit "7") within each byte                                                                                 | Compliant              | Status entries are packed from the least significant bit toward the most significant bit within each byte, matching the draft examples.                                                              |
| 4  | §4.2 / §4.3 | `bits` ∈ {1, 2, 4, 8}                                                                                                                      | Compliant              | New status lists use the draft-supported bit widths, and compatible existing lists are preserved or repacked without emitting unsupported widths.                                                    |
| 5  | §4.2        | `lst` is base64url of the compressed array, no padding                                                                                     | Compliant              | JWT status lists expose the compressed byte array as unpadded base64url, and empty lists are emitted as a valid compressed empty stream.                                                             |

| 8  | §5.1        | `sub` MUST be the URI of the Status List Token, equal to the Referenced Token's `status_list.uri`                                          | Compliant              | Published status lists use a subject URI that resolves to the status-list retrieval endpoint.                                                                                                        |
| 9  | §5.1        | `iat` REQUIRED; `exp` / `ttl` RECOMMENDED                                                                                                  | Compliant              | Issued status list tokens include issuance time, expiration time, and time-to-live claims.                                                                                                           |
| 10 | §5.2        | CWT protected header label `16` (type) MUST be the full media type `application/statuslist+cwt` (or the registered CoAP Content-Format ID) | **Fixed**              | CWT status list tokens now use the full media type in the protected type header rather than the JWT abbreviation.                                                                                    |
| 11 | §5.2        | CWT MUST NOT carry the CWT tag ([RFC 8392] §6); the COSE message MUST be `COSE_Sign1_Tagged` (18) or `COSE_Mac0_Tagged` (17)               | **Fixed**              | CWT responses now emit a tagged COSE message as required by the draft, changing the CWT wire encoding to the compliant form.                                                                         |
| 12 | §5.2        | CWT claim keys: `2` (sub), `6` (iat), `4` (exp), `65534` (ttl), `65533` (status_list)                                                      | Compliant              | CWT status list tokens use the draft-defined integer claim keys.                                                                                                                                     |
| 13 | §4.3 / §5.2 | CBOR `status_list.lst` MUST be a CBOR byte string (major type 2) of the raw compressed bytes; `bits` MUST be a CBOR unsigned integer       | **Fixed**              | CWT status list tokens now encode the compressed list as raw CBOR bytes and keep the bit width as an unsigned integer.                                                                               |
| 14 | §7.1        | Status Type registry: `0x03` and `0x0C`-`0x0F` permanently reserved as application-specific; all others reserved for future registration   | Compliant              | The API accepts the draft-defined standard and application-specific values and rejects reserved values.                                                                                              |
| 15 | §8.1        | Media types `application/statuslist+jwt` / `application/statuslist+cwt` for content negotiation and `Content-Type`                         | Compliant              | Status-list retrieval uses the registered JWT and CWT media types for negotiation and responses.                                                                                                     |
| 16 | §8.2        | Successful response MUST use a 2xx status code                                                                                             | Compliant              | Successful status-list retrieval returns a 2xx response.                                                                                                                                             |
| 17 | §8.2        | `Content-Encoding` (e.g. gzip) via RFC 9110 negotiation, RECOMMENDED for Status List Tokens **in JWT format**                              | Hardening note         | Current responses are compressed without honoring the client's content-encoding negotiation and without limiting that behavior to JWT responses. SHOULD-level; not fixed in this change.             |
| 18 | §8.4        | Historical resolution via a `?time=` query parameter                                                                                       | Compliant              | Historical status-list retrieval is supported for retained snapshots; unavailable times return not found. This optional feature retains timing data and therefore carries the §12.7 privacy warning. |

| 20 | §13.2/§13.3 | Prevent double allocation                                                                                                                  | **Fixed**              | The management API provides fixed-size list allocation, records reservations durably, and rejects updates to unallocated fixed-size indices with `409 index_not_allocated`.                          |
| 21 | §5.1 / §5.2 | `ttl` MUST be a positive number; lifetimes must be positive (`>= 1`) with `ttl < exp` within `MAX_TOKEN_LIFETIME_SECS`                     | **Fixed**              | `ttl = 0` was accepted before this change; `StatusListConfig::validate()` (`src/config.rs`) now rejects `0`, `ttl >= exp`, and values above the one-year ceiling at startup with a clear error naming the env var; expiry construction fails closed via `checked_add` on overflow.
