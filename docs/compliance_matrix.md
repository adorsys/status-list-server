# OAuth Token Status List - draft-21 Compliance Matrix

Audit of the status-list issuer/hosting implementation against
[draft-ietf-oauth-status-list-21](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/)
(Token Status List, expires 23 December 2026). All findings below were checked directly
against the primary IETF text. Complements the application-specific status value work
tracked in #152.

Status legend:

- **Compliant** - behavior matches the spec, verified by reading the code (and, where noted, a test).
- **Fixed** - deviated from the spec; corrected in this change.
- **Deviation (documented)** - intentional gap; the spec marks the feature OPTIONAL and no
  ticket deliverable requires it.
- **Out of scope** - belongs to another tracked ticket or component.
- **Hardening note** - not a draft-21 violation (SHOULD-level or unspecified), but worth
  tracking as a follow-up.

| 8   | §5.1        | `sub` MUST be the URI of the Status List Token, equal to the Referenced Token's `status_list.uri`                                          | Compliant              | The `sub` claim is built from the server domain and list id at publish time, resolving to the actual endpoint that serves the status list.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 9   | §5.1        | `iat` REQUIRED; `exp` / `ttl` RECOMMENDED                                                                                                  | Compliant              | Live tokens carry all three claims. `iat` is `max(window_start, updated_at)` — anchored to the start of a validity window, or to the last content change if it is later, so a mid-window revocation never mints a token claiming to predate the change — with `exp = iat + exp_secs`. The window is capped at `min(exp - ttl, ttl)` so `iat + ttl` is always in the future (draft-21 §13.7 "refresh at `iat + ttl`" never loops) and a 304's `max-age = ttl` never outlives the token it vouches for. The weak ETag (`W/"..."`) is derived from the representation identity (`list_id, content_hash, signer_fingerprint, window_start, format, encoding`), not the signed bytes, so it is stable across replicas and restarts (ECDSA signatures are randomized) and never needs a sign to answer a 304. The server validates `ttl < exp` at startup (a `ttl >= exp` or `exp == 0` config is refused) and, defensively, the conditional logic certifies a 304 only while `now + ttl <= exp`, degrading to a re-signed `200` otherwise. A signed-bytes cache reuses one sign per `(list, window, format)` per replica and expires each entry at the end of its own window.                                                                                                                                |

It now emits the full `application/statuslist+cwt` media type, pinned by a test that asserts the value in the COSE protected header.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 11  | §5.2        | CWT MUST NOT carry the CWT tag ([RFC 8392] §6); the COSE message MUST be `COSE_Sign1_Tagged` (18) or `COSE_Mac0_Tagged` (17)               | **Fixed**              | The COSE message is now emitted tagged (`COSE_Sign1_Tagged`, CBOR tag 18), matching the spec's own worked example and the repo's documented wire-format hex dump; the in-repo consumer verifies it by decoding the tagged form. This changes the CWT endpoint's wire bytes for any external consumer.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 12  | §5.2        | CWT claim keys: `2` (sub), `6` (iat), `4` (exp), `65534` (ttl), `65533` (status_list)                                                      | Compliant              | The CWT claim keys match the spec integers. The test asserts these against the literal spec values rather than re-deriving them from the same constants used to build the claims.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 13  | §4.3 / §5.2 | CBOR `status_list.lst` MUST be a CBOR byte string (major type 2) of the raw compressed bytes; `bits` MUST be a CBOR unsigned integer       | **Fixed**              | The CWT representation previously emitted `lst` as a CBOR text string of the base64url value (correct for the JSON/JWT representation, wrong for CBOR). It now decodes the stored base64url `lst` back to raw compressed bytes and emits them as a CBOR byte string; `bits` is emitted as a CBOR unsigned integer. The test was hardened to assert the byte-string form against the raw compressed bytes.                                                                                                                                                                                                                                                                                                                                                             |
| 14  | §7.1        | Status Type registry: `0x03` and `0x0C`-`0x0F` permanently reserved as application-specific; all others reserved for future registration   | Compliant              | Request parsing and domain encoding accept status values `0`, `1`, `2`, `3`, and `12`-`15`; reserved values `4`-`11` and `16`-`255` are rejected, and stored reserved values encountered while decoding are classified as corrupt stored state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 15  | §8.1        | Media types `application/statuslist+jwt` / `application/statuslist+cwt` for content negotiation and `Content-Type`                         | Compliant              | The two media types are returned verbatim as `Content-Type` and drive content negotiation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 16  | §8.2        | Successful response MUST use a 2xx status code                                                                                             | Compliant              | Successful live and historical responses return `200 OK`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

This optional feature retains timing data and therefore carries the §12.7 privacy warning.                                                                                                                                                                                                                                                                                                                                                                                                 |
