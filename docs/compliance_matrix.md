# OAuth Token Status List - draft-21 Compliance Matrix

Requirements and observable behavior of the status-list issuer and hosting service
against [draft-ietf-oauth-status-list-21](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/21/).

Status legend:

- **Compliant** - behavior matches the specification.
- **Limitation** - a restriction or interoperability difference described in the notes.
- **Out of scope** - outside the status-list protocol or handled by a separate component.

| #  | Spec §        | Requirement                                                                                                                                | Status       | Observable behavior / limitations                                                                                                                                                                                                                                                                                                                                                                                    |
| --- | --------- | ----------- | ------ | ------------------------------ |
| 1  | §4.1          | Byte array compressed with DEFLATE ([RFC 1951]) in the ZLIB ([RFC 1950]) container                                                         | Compliant    | Status-list bytes are zlib-wrapped DEFLATE, including the zlib header and checksum trailer. Empty lists also produce a valid compressed empty stream.                                                                                                                                                                                                                                                                |
| 2  | §4.1          | Highest compression level RECOMMENDED                                                                                                      | Compliant    | Status-list compression uses `flate2`’s `Compression::best()` (level 9). Compressed bytes may differ between conforming encoders while representing the same status values.                                                                                                                                                                                                                                              |
| 3  | §4.1          | Bits packed LSB (bit "0") → MSB (bit "7") within each byte                                                                                 | Compliant    | Status entries are packed from the least significant bit toward the most significant bit within each byte, matching the draft examples.                                                                                                                                                                                                                                                                              |
| 4  | §4.2 / §4.3   | `bits` ∈ {1, 2, 4, 8}                                                                                                                      | Compliant    | JWT and CWT responses emit only the supported widths. Stored data with an unsupported width is repacked when representable; corrupt stored data fails retrieval with HTTP `500`.                                                                                                                                                                                                                                     |
| 5  | §4.2          | `lst` is base64url of the compressed array, no padding                                                                                     | Compliant    | JWT `lst` values contain the compressed status-list bytes encoded as unpadded base64url.                                                                                                                                                                                                                                                                                                                             |
| 6  | §4.2 / §9     | `aggregation_uri` (OPTIONAL) and the §9.3 Status List Aggregation it points to                                                             | Compliant    | Tokens advertise an issuer-scoped aggregation URI under an opaque ID only when configured and that issuer’s aggregation fits one page. A failed ID lookup omits the claim.                                                                                                                                                                                                                                           |
| 7  | §5.1          | JWT `typ` header MUST be the abbreviated `statuslist+jwt`                                                                                  | Compliant    | JWT status-list tokens carry `typ=statuslist+jwt`.                                                                                                                                                                                                                                                                                                                                                                   |
| 8  | §5.1          | `sub` MUST be the URI of the Status List Token, equal to the Referenced Token’s `status_list.uri`                                          | Compliant    | The signed `sub` equals the published status-list URI used to retrieve the token.                                                                                                                                                                                                                                                                                                                                    |
| 9  | §5.1          | `iat` REQUIRED; `exp` / `ttl` RECOMMENDED                                                                                                  | Compliant    | Tokens include `iat`, `exp`, and a positive `ttl`, with `iat < exp`.                                                                                                                                                                                                                                                                                                                                                 |
| 10 | §5.2          | CWT protected header label `16` (type) MUST be the full media type `application/statuslist+cwt` (or the registered CoAP Content-Format ID) | Compliant    | The protected CWT type header uses label `16` with the value `application/statuslist+cwt`.                                                                                                                                                                                                                                                                                                                           |
| 11 | §5.2          | CWT MUST NOT carry the CWT tag ([RFC 8392] §6); the COSE message MUST be `COSE_Sign1_Tagged` (18) or `COSE_Mac0_Tagged` (17)               | Compliant    | CWT responses are tagged COSE_Sign1 messages (tag 18, leading byte `0xd2`); the claims map has no enclosing CWT tag 61.                                                                                                                                                                                                                                                                                              |
| 12 | §5.2          | CWT claim keys: `2` (sub), `6` (iat), `4` (exp), `65534` (ttl), `65533` (status_list)                                                      | Compliant    | CWT claims use the specified numeric labels. The `ttl` value is an unsigned integer greater than zero.                                                                                                                                                                                                                                                                                                               |
| 13 | §4.3 / §5.2   | CBOR `status_list.lst` MUST be a CBOR byte string (major type 2) of the raw compressed bytes; `bits` MUST be a CBOR unsigned integer       | Compliant    | CWT `lst` is a CBOR byte string containing the raw compressed bytes; `bits` is an unsigned integer.                                                                                                                                                                                                                                                                                                                  |
| 14 | §7.1          | Status Type registry: `0x03` and `0x0C`-`0x0F` permanently reserved as application-specific; all others reserved for future registration   | Compliant    | The API accepts the draft-defined standard and application-specific values and rejects reserved values.                                                                                                                                                                                                                                                                                                              |
| 15 | §8.1          | Media types `application/statuslist+jwt` / `application/statuslist+cwt` for content negotiation and `Content-Type`                         | Limitation   | See the status-list GET operation in [OpenAPI](openapi.yaml) for negotiation behavior. Non-`q` media parameters are ignored under a documented parameter-agnostic policy, a deviation from RFC 9110 §12.5.1.                                                                                                                                                                                                         |
| 16 | §8.2          | Successful response MUST use a 2xx status code                                                                                             | Compliant    | Successful status-list retrieval returns a 2xx response.                                                                                                                                                                                                                                                                                                                                                             |
| 17 | §8.2          | `Content-Encoding` (e.g. gzip) via RFC 9110 negotiation, RECOMMENDED for Status List Tokens **in JWT format**                              | Compliant    | See the status-list GET operation in [OpenAPI](openapi.yaml) for `Accept-Encoding` behavior. CWT responses are never gzip-encoded.                                                                                                                                                                                                                                                                                   |
| 18 | §8.4          | Historical resolution via a `?time=` query parameter                                                                                       | Limitation   | History is enabled by default for 90 days (`APP_STATUS_LIST__SNAPSHOT_RETENTION_SECS=7776000`); set it to `0` to disable snapshots. Malformed, zero, negative, and future times return `400`; a valid time without a retained snapshot returns `404`. With snapshots disabled, requests still return `404`, though draft-21 says unsupported `time` SHOULD return `501`. History has the §12.7 privacy implications. |
| 19 | §11.5 / §13.7 | Caching MUST NOT extend a Status List Token beyond its `exp`                                                                               | Compliant    | The response `max-age` is capped at the token’s remaining lifetime. A conditional request never receives `304` once the cached token has expired. See the status-list GET operation in [OpenAPI](openapi.yaml).                                                                                                                                                                                                      |
| 20 | -             | Publish/update REST endpoints                                                                                                              | Out of scope | This server’s management API is issuer-internal tooling; draft-21 governs the status-list token format and retrieval behavior, not issuer-internal management workflows.                                                                                                                                                                                                                                             |
| 21 | §13.3         | Prevent double allocation                                                                                                                  | Compliant    | Allocation rows are separate from the list row; indices are selected and inserted in one transaction while the parent list is locked.                                                                                                                                                                                                                                                                                |
| 22 | §13.3         | Duplicate index in a single request                                                                                                        | Compliant    | Publish and update requests containing the same `index` more than once are rejected with `400 duplicate_index` before any status-list write is applied.                                                                                                                                                                                                                                                              |
| 23 | §10           | X.509 EKU for the signing certificate                                                                                                      | Out of scope | Certificate provisioning is a separate component.                                                                                                                                                                                                                                                                                                                                                                    |
| 24 | §5.1 / §5.2   | `ttl` MUST be a positive number; lifetimes must be positive (`>= 1`) with `ttl < exp` within the configured maximum token lifetime         | Compliant    | Configuration rejects non-positive or excessive token lifetimes and requires `ttl` to be shorter than the token validity period. Token expiry overflow is rejected.                                                                                                                                                                                                                                                  |
| 25 | §8.1          | CORS permits cross-origin GET requests                                                                                                     | Compliant    | Cross-origin GET and preflight requests are supported. ETag is not exposed to browser JavaScript.                                                                                                                                                                                                                                                                                                                    |
| 26 | §9.3          | Aggregation returns published status-list URIs                                                                                             | Compliant    | Issuer-scoped aggregation returns that issuer’s published status-list URIs. The legacy endpoint includes all issuers. Empty results are arrays; `next_cursor` is null on the terminal page. Unpaged requests fail if the result exceeds one page.                                                                                                                                                                    |
| 27 | Appendix C    | Published reference vectors                                                                                                                | Limitation   | The status contents match C.1/C.2 after decompression; byte-for-byte compressed output is not guaranteed. C.3/C.4 contain reserved status values that the API rejects.                                                                                                                                                                                                                                               |
