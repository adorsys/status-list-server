# OAuth Token Status List - draft-21 Compliance Matrix

Requirements and observable behavior of the status-list issuer and hosting service
against [draft-ietf-oauth-status-list-21](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/21/).

Status legend:

- **Compliant** - behavior matches the specification.
- **Limitation** - a restriction or interoperability difference described in the notes.
- **Out of scope** - outside the status-list protocol or handled by a separate component.

| #  | Spec §      | Requirement                                                                                                                                | Status       | Observable behavior / limitations                                                                                                                                                                    |
| -- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1  | §4.1        | Byte array compressed with DEFLATE ([RFC 1951]) in the ZLIB ([RFC 1950]) container                                                         | Compliant    | Status lists contain zlib-wrapped DEFLATE bytes, including the zlib header and checksum trailer.                                                                                                     |
| 2  | §4.1        | Highest compression level RECOMMENDED                                                                                                      | Compliant    | Status lists use the highest available compression level. Compressed bytes may differ between conforming encoders while representing the same status values.                                         |
| 3  | §4.1        | Bits packed LSB (bit "0") → MSB (bit "7") within each byte                                                                                 | Compliant    | Status entries are packed from the least significant bit toward the most significant bit within each byte, matching the draft examples.                                                              |
| 4  | §4.2 / §4.3 | `bits` ∈ {1, 2, 4, 8}                                                                                                                      | Compliant    | Status lists use only the supported bit widths: 1, 2, 4, or 8.                                                                                                                                       |
| 5  | §4.2        | `lst` is base64url of the compressed array, no padding                                                                                     | Compliant    | JWT `lst` values contain the compressed status-list bytes encoded as unpadded base64url.                                                                                                             |
| 6  | §4.2 / §9   | `aggregation_uri` (OPTIONAL)                                                                                                               | Compliant    | JWT and CWT status lists include `aggregation_uri` when configured and omit it when unset or blank.                                                                                                  |
| 7  | §5.1        | JWT `typ` header MUST be the abbreviated `statuslist+jwt`                                                                                  | Compliant    | JWT status-list tokens carry `typ=statuslist+jwt`.                                                                                                                                                   |
| 8  | §5.1        | `sub` MUST be the URI of the Status List Token, equal to the Referenced Token's `status_list.uri`                                          | Compliant    | The signed `sub` equals the published status-list URI used to retrieve the token.                                                                                                                    |
| 9  | §5.1        | `iat` REQUIRED; `exp` / `ttl` RECOMMENDED                                                                                                  | Compliant    | Tokens include `iat`, `exp`, and a positive `ttl`, with `iat < exp`.                                                                                                                                 |
| 10 | §5.2        | CWT protected header label `16` (type) MUST be the full media type `application/statuslist+cwt` (or the registered CoAP Content-Format ID) | Compliant    | The protected CWT type header uses label `16` with the value `application/statuslist+cwt`.                                                                                                           |
| 11 | §5.2        | CWT MUST NOT carry the CWT tag ([RFC 8392] §6); the COSE message MUST be `COSE_Sign1_Tagged` (18) or `COSE_Mac0_Tagged` (17)               | Compliant    | CWT responses are tagged COSE Sign1 messages (tag 18, leading byte `0xd2`); the claims map has no enclosing CWT tag 61.                                                                              |
| 12 | §5.2        | CWT claim keys: `2` (sub), `6` (iat), `4` (exp), `65534` (ttl), `65533` (status_list)                                                      | Compliant    | CWT claims use the specified numeric labels. The `ttl` value is an unsigned integer greater than zero.                                                                                               |
| 13 | §4.3 / §5.2 | CBOR `status_list.lst` MUST be a CBOR byte string (major type 2) of the raw compressed bytes; `bits` MUST be a CBOR unsigned integer       | Compliant    | CWT `lst` contains the raw compressed bytes as a CBOR byte string; `bits` is an unsigned integer in {1, 2, 4, 8}.                                                                                    |
| 14 | §7.1        | Status Type registry: `0x03` and `0x0C`-`0x0F` permanently reserved as application-specific; all others reserved for future registration   | Compliant    | The API accepts the draft-defined standard and application-specific values and rejects reserved values.                                                                                              |
| 15 | §8.1        | Media types `application/statuslist+jwt` / `application/statuslist+cwt` for content negotiation and `Content-Type`                         | Compliant    | JWT and CWT responses use their respective status-list media types. Aggregation responses use `application/json`.                                                                                    |
| 16 | §8.2        | Successful response MUST use a 2xx status code                                                                                             | Compliant    | Successful status-list retrieval returns a 2xx response.                                                                                                                                             |
| 17 | §8.2        | `Content-Encoding` (e.g. gzip) via RFC 9110 negotiation, RECOMMENDED for Status List Tokens **in JWT format**                              | Compliant    | Current and historical JWT responses support negotiated gzip encoding, including wildcard requests. CWT responses are not gzip-encoded.                                                              |
| 18 | §8.4        | Historical resolution via a `?time=` query parameter                                                                                       | Compliant    | Historical status-list retrieval is supported for retained snapshots; unavailable times return not found. This optional feature retains timing data and therefore carries the §12.7 privacy warning. |
| 19 | -           | Publish/update REST endpoints                                                                                                              | Out of scope | This server's management API is issuer-internal tooling; draft-21 governs the status-list token format and retrieval behavior, not issuer-internal management workflows.                             |
| 20 | §13.2/§13.3 | Prevent double allocation                                                                                                                  | Compliant    | The management API provides fixed-size list allocation, records reservations durably, and rejects updates to unallocated fixed-size indices with `409 index_not_allocated`.                          |
| 21 | §13.3       | Duplicate index in a single request                                                                                                        | Compliant    | Publish and update requests containing the same `index` more than once are rejected with `400 duplicate_index` before any status-list write is applied.                                              |
| 22 | §10         | X.509 EKU for the signing certificate                                                                                                      | Out of scope | Certificate provisioning is a separate component.                                                                                                                                                    |
| 23 | §5.1 / §5.2 | `ttl` MUST be a positive number; lifetimes must be positive (`>= 1`) with `ttl < exp` within the configured maximum token lifetime         | Compliant    | Configuration rejects non-positive or excessive token lifetimes and requires `ttl` to be shorter than the token validity period. Token expiry overflow is rejected.                                  |
| 24 | §8          | CORS permits cross-origin GET requests                                                                                                     | Compliant    | Cross-origin GET and preflight requests are supported. ETag is not exposed to browser JavaScript.                                                                                                    |
| 25 | §9.3        | Aggregation returns published status-list URIs                                                                                             | Compliant    | Aggregation returns published status-list URIs in a JSON array, including an empty array when no lists exist. Responses include `next_cursor`, which is null on the terminal page.                   |
| 26 | Appendix C  | Published reference vectors                                                                                                                | Limitation   | The status contents match C.1/C.2 after decompression; byte-for-byte compressed output is not guaranteed. C.3/C.4 contain reserved status values that the API rejects.                               |
